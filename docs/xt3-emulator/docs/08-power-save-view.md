# Power-save view: why the live view does not wake on half-press

X-T3 firmware 5.11, XP4 emulator. Runs v18i–v18o of 2026-11-13. Every run started from the same configured-body NOR,
used the same plan timings and the same binary (SHA-256 prefix `a4699643`), and finished identically
(3.8 G instructions, same final PC). Counted execution (`FUJIMOD_XP4_COUNTED=1`) gave the same results as the
per-instruction hook: 211/211 peeks, 29/29 samples and the same write instants.

## Symptom

About 12 s after the last key press, the camera relaunches its live view in power-save mode. A half-press (S1) then
never brings the normal live view back. The LV controller keeps waiting for one completion, which never comes.

## Established cause (100 %)

- In power-save view, the sensor runs in mode `0x8d`. The display-path predicate that the imaging task uses is false
  for this mode, so the pipeline never reports completion. That completion is what releases the half-press wake.
- The mode is chosen on purpose by the firmware when it enters power-save. It is not caused by a different
  setting. The decision chain, measured with call and memory watches:
  1. The LV controller handles the "enter power-save" request. A block copy fills its request block (`0x028DD004`),
     and that copy sets the flag at `+0x594` to 1. In the earlier, non-power-save requests this flag is 0.
  2. The request is forwarded to the imaging task (message `0x1443`). A loader maps flag bit 0 to bit 2 of the
     LV-condition mask (`+0x92`).
  3. On power-save entry the firmware copies settings set 0 into set 1 and makes set 1 active. It then writes
     the mask value 4 into set 1 (job `0xBA`).
  4. With mask bit 2 set, the sensor-mode calculator takes its "column 0" branch. Its mode table pairs `0x8d`
     (power-save) with `0x8e` (normal), so the mode becomes `0x8d`.
- Checked and excluded: the two settings fields first suspected (`+0x94`, `+0x206C`), the mask override switch,
  a second input byte, and the only settings-bank byte on this path (`0xC0000 + 0xE18`). None of them changes
  across the power-save entry.

## What this means

- **Not a settings difference (85 %).** No persistent setting is read on the observed decision chain. That
  covers the settings bank at NOR `0xC0000` and the settings journal at `0x3FA0000`. Caveat: the origin of the
  copied request block is identified only up to the copy itself.
- **Mode choice is normal firmware behaviour (85 %).** Selecting the power-save sensor mode in power-save view is
  intended.
- **Real-body wake is still to measure on hardware.** On a real X-T3, any operation is expected to leave
  power-save view (70 %). If so, real hardware delivers something in mode `0x8d` that the emulator does not:
  a pipeline-completion event or a sensor response specific to that mode. This is the remaining open point. It
  belongs to the emulated hardware, not to the camera settings.

## Reproduce

The run plans are `plan-veille-v18i-temoin` to `plan-veille-v18o-temoin`. They share the same timings and differ
only in their call watches, memory watches and peek ranges. Each plan is generated by a small script from the
previous one. Both the plans and the scripts are kept with the project's run files; they are not yet in
[reproduce.md](reproduce.md).
